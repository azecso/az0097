> الحالة: **مقترحة — بانتظار اعتماد المالك**. لم يُكتب أي كود إنتاجي.

## ADR-001 — اختيار التقنية: Next.js + PostgreSQL مقابل Laravel + PostgreSQL

### السياق
نظام محاسبي عربي RTL، مستخدمان فقط، نشاط واحد، PWA بوضع offline للمسودات، مزامنة بتحقق خادم، تقارير PDF عربية وExcel، يعمل على VPS صغير بـ Docker.

### المقارنة (1 ضعيف … 5 ممتاز، تقدير مهني لا قياس)

| المعيار (وزن) | Next.js (TypeScript) | Laravel (PHP) | ملاحظات |
|---|---|---|---|
| PWA وOffline (25%) | **5** — الواجهة وIndexedDB وService Worker بنفس اللغة، ويمكن مشاركة مخططات التحقق (Zod) بين العميل والخادم | 3 — يحتاج واجهة JS منفصلة (Vue/React/Inertia) فتتكرر قواعد التحقق | القلب الصعب في المشروع هو المزامنة، وليس CRUD |
| الأدوات المحاسبية الجاهزة (15%) | 2 — لا قالب ERP؛ نبني Auth/RBAC/Audit | **4** — Policies، Queues، Migrations، Validation، Excel (maatwebsite) | تقليل العمل المبدئي لصالح Laravel |
| دقة المال (decimal) (10%) | 4 — `decimal.js` أو `bigint` بالفلس؛ يتطلب انضباطاً | 4 — `brick/money` أو `bcmath` | متعادلان؛ القاعدة الحاسمة: NUMERIC في DB + منع float بالـ lint |
| PDF عربي RTL (10%) | **5** — Chromium headless (Playwright) من HTML: تشكيل عربي كامل وخطوط (Cairo/Noto Naskh) | 3 — mPDF جيد لكن يحتاج ضبطاً؛ DomPDF ضعيف بالعربية؛ أو Browsershot (Chromium أيضاً) | الحل الأمثل في الحالتين: Chromium |
| أداء التقارير (10%) | 4 — SQL مباشر/Views | 4 — نفسه | الأداء محكوم بـ PostgreSQL وليس الإطار |
| الاختبارات (10%) | 4 — Vitest/Playwright + اختبارات DB حقيقية بـ Testcontainers | **5** — PHPUnit/Pest مع DB transactions مدمجة | |
| الصيانة وتوفر المطورين (10%) | 4 — TypeScript بنوع صارم يقلل أخطاء مالية | 4 — Laravel مستقر جداً | |
| Docker/موارد VPS (5%) | 3 — Node يستهلك أكثر قليلاً | **4** — PHP-FPM أخف | فارق بسيط |
| التكلفة (5%) | متساوية — كلاهما مفتوح المصدر؛ التكلفة الحقيقية هي الاستضافة | | |

**المجموع الموزون التقريبي:** Next.js ≈ **4.0** ، Laravel ≈ **3.8** — فارق صغير. القرار ليس «الأفضل مطلقاً»، بل الأنسب لهذه المتطلبات.

### القرار
**Next.js (App Router) + TypeScript صارم + PostgreSQL 16**، كـ **Modular Monolith** (خدمة واحدة، وحدات منفصلة داخلياً) وليس Microservices.

### المبررات الحاسمة
1. أصعب جزء هو offline sync؛ لغة واحدة وقواعد تحقق مشتركة تقلل التباين بين العميل والخادم.
2. الـ PDF العربي عبر Chromium أدق حل في الحالتين، وNode يدمجه أسهل.
3. **سلامة الدفتر لا تعتمد على الإطار**: تُفرض داخل PostgreSQL نفسه (انظر ADR-003) فيبقى الاختيار قابلاً للمراجعة دون خطر محاسبي.

### المخاطر والتخفيف
| الخطر | التخفيف |
|---|---|
| لا يوجد RBAC/Audit جاهز | طبقة `authz` مركزية + اختبارات صلاحيات إلزامية (Phase 1) |
| انزلاق float في JS | قاعدة ESLint تمنع `parseFloat`/`Number` على المال، وكل المبالغ `string` ↔ `NUMERIC` عبر `decimal.js` |
| Chromium ثقيل على VPS صغير | توليد PDF بطابور تزامن = 1، وتخصيص ≥ 2GB RAM |
| ORM يخفي القفل والمعاملات | استخدام Drizzle ORM + SQL خام لعمليات FIFO/الترحيل (`SELECT … FOR UPDATE`) |

### البديل
إن كان فريق الصيانة لديك يعرف PHP/Laravel أكثر، فـ Laravel قرار مقبول؛ والمخطط (ERD/القيود/FIFO/المزامنة) في هذا الـ Phase مستقل عن الإطار ولن يتغير.

## ADR-002 — الاستضافة والنشر

### المبدأ
لا أفترض أسعاراً ولا أذكر منتجاً بسعر. المالك يزودني بعروض الأسعار الفعلية وقت Phase 6؛ هنا المعايير والحد الأدنى التقني.

### الحد الأدنى التقني (تقدير هندسي، يحتاج قياساً في Phase 6)
| المورد | الحد الأدنى للتشغيل الفعلي | سبب |
|---|---|---|
| vCPU | 2 | تطبيق + PostgreSQL + Chromium عند الطلب |
| RAM | **2GB حداً أدنى، 4GB مريح** | PostgreSQL ~0.5GB، Node ~0.5GB، Chromium ~0.5–1GB وقت طباعة |
| تخزين | 40GB SSD | قاعدة صغيرة + مرفقات + سجلات؛ مع نمو الصور |
| نظام | Ubuntu LTS + Docker Engine + Compose v2 | |
| شبكة | IPv4 ثابت + HTTPS على 443 | |

### الفئات المقارنة
| المعيار | VPS منخفض التكلفة (Docker Compose) | Managed PaaS (تطبيق + DB مُدارة) | Shared Hosting |
|---|---|---|---|
| دعم Docker وPostgreSQL | كامل | يختلف حسب المزود | **غير مفترض — لا يُعتمد** |
| نسخ احتياطي | علينا نبنيه (restic + تخزين خارجي) — مضمون السيطرة | غالباً مدمج (تحقق من الاحتفاظ وPITR) | محدود |
| الصيانة | علينا (تحديثات، أمن، مراقبة) | أقل | أقل لكن غير مناسب |
| التحكم بالبيانات والموقع | كامل | حسب المنطقة | محدود |
| قابلية النمو | رفع الباقة/نقل | سهلة | ضعيفة |
| **التوصية** | **الخيار الأنسب كبداية** مقابل مرونة وتكلفة ثابتة متوقعة | بديل إن لم يتوفر من يدير الخادم | مرفوض |

### قرار مقترح
**VPS واحد + Docker Compose** (Caddy ← App ← PostgreSQL) + **نسخ احتياطي مشفّر إلى تخزين خارجي S3-compatible مختلف عن مزود الـ VPS**. يُختار المزود وقت النشر بعد مقارنة الأسعار الفعلية.

### قائمة تحقق لاختيار المزود (يجيب عنها المالك/المزود)
- هل الموقع الجغرافي يخدم زمن الاستجابة وقانونية البيانات لديك؟
- لقطات (snapshots) مجانية أم مدفوعة؟ ولا تُحسب نسخاً احتياطية خارجية.
- IPv4 ثابت، وصول SSH بمفاتيح، وجدار حماية.
- سياسة عدم إنهاء الخدمة المفاجئ، وطرق الدفع المتاحة محلياً.

### بنية Compose (تصميم فقط)
```
caddy (80/443, TLS تلقائي) → app (Next.js, non-root, read-only FS, healthcheck)
                              ↘ db (postgres:16, volume, ليس مكشوفاً للخارج)
backup (cron: pg_dump | age | restic → تخزين خارجي)
```
- شبكتان: `edge` (caddy↔app) و`internal` (app↔db)؛ قاعدة البيانات لا منفذ لها على المضيف.
- الأسرار عبر Docker secrets/ملف `.env` غير مُرفوع؛ `.env.example` فقط في المستودع.

### سياسة النسخ الاحتياطي
| النوع | الجدولة | الاحتفاظ | ملاحظات |
|---|---|---|---|
| يومي | 02:00 محلي | 14 يوماً | `pg_dump -Fc` + المرفقات |
| أسبوعي | الجمعة | 8 أسابيع | |
| شهري | أول الشهر | 12 شهراً | |
| التشفير | `age` أو restic المشفّر | المفتاح خارج الخادم | فقدان المفتاح = فقدان النسخة؛ يحفظه المالك |
| اختبار الاستعادة | شهرياً آلياً على بيئة منفصلة + تقرير | | معيار قبول Phase 6 |

## ADR-003 — الدفتر المزدوج: سلامة مفروضة في قاعدة البيانات

### القرار
كل مستند مرحّل ينتج `journal_entries` + `journal_lines` داخل **معاملة واحدة**، وتُفرض القواعد داخل PostgreSQL:
1. `CHECK` أن كل سطر إما مدين أو دائن (وليس كليهما) وأن القيمة ≥ 0.
2. **Constraint Trigger (DEFERRABLE INITIALLY DEFERRED)**: مجموع المدين = مجموع الدائن لكل قيد عند COMMIT (بالعملة الأساس).
3. **Trigger منع التعديل/الحذف** على القيود والسطور وعلى المستندات بحالة `POSTED`؛ التصحيح بمستند عكسي فقط.
4. لا `ON DELETE CASCADE` على أي جدول مالي (`RESTRICT` دائماً).
5. التعامل مع `float` ممنوع: `NUMERIC(20,4)` للمبالغ، `NUMERIC(20,6)` للكميات، `NUMERIC(18,8)` لأسعار الصرف.

### النتيجة
حتى لو أخطأ كود التطبيق، لن يُحفظ قيد غير متوازن ولن يُعدَّل مرحّل.

## ADR-004 — FIFO بالدفعات مع قفل متزامن

### القرار
`stock_lots` طبقة لكل (صنف، موقع، دفعة). الاستهلاك:
1. داخل معاملة `SERIALIZABLE`-بديل: `READ COMMITTED` + `SELECT … FROM stock_lots WHERE product_id=? AND location_id=? AND qty_remaining>0 ORDER BY received_at, id FOR UPDATE`.
2. أخذ الأقفال بترتيب ثابت (product_id ثم location_id) لتجنب deadlock؛ مع إعادة المحاولة عند 40001/40P01.
3. `CHECK (qty_remaining >= 0)` يمنع الرصيد السالب على مستوى DB.
4. كل استهلاك يكتب `stock_lot_consumptions` (سطر البيع/النقل ↔ الطبقة ↔ الكمية ↔ التكلفة) فيمكن عكسه بدقة وتتبع تكلفة المصدر.

التفاصيل الخوارزمية في `03-accounting-design.md` §4.

## ADR-005 — Audit Trail

- جدول `audit_logs` للإضافة فقط (append-only، منع UPDATE/DELETE بـ trigger).
- يُسجَّل: المستخدم، الوقت، العملية، الكيان، المعرّف، قبل/بعد (JSONB)، IP، device_id، سبب (إلزامي عند الإلغاء/العكس).
- التصحيح = مستند عكسي مرتبط `reverses_id` + سبب + اعتماد.
- سلسلة تجزئة اختيارية (`prev_hash`,`hash`) لكشف العبث، ويتم تفعيلها في Phase 6 إن رغب المالك.

## ADR-006 — العزل والحدود

- `company_id` على كل جدول، مع Row-Level Security كحزام أمان (السياسة: `company_id = current_setting('app.company_id')::uuid`) — النشاط واحد اليوم لكنه يمنع تسرباً مستقبلياً.
- صلاحيات الخادم تُفحص في طبقة الخدمة، وليس في الواجهة فقط.
- دور DB للتطبيق **بلا** صلاحية `DROP/TRUNCATE`، ودور منفصل للـ migrations.

## ADR-007 — المصادقة والجلسات

- Argon2id لكلمات المرور (معاملات OWASP الحالية).
- جلسات في DB، كوكي `HttpOnly; Secure; SameSite=Lax`، دوران معرف الجلسة عند الدخول، انتهاء خمول قابل للضبط.
- CSRF: رمز مزامنة (double-submit) لكل تعديل + فحص Origin.
- Rate limit على الدخول والـ API (حسب IP والمستخدم) وقفل مؤقت عند الفشل.
- TOTP 2FA مفعّل للمالك افتراضياً (اختياري للمحاسب).
- Content-Security-Policy صارمة، ترميز خروج تلقائي (React)، استعلامات parameterized فقط.

## ADR-008 — الأوفلاين

ملخصه: **المسودات فقط**، لا ترقيم نهائي ولا ترحيل ولا FIFO دون الخادم؛ مزامنة idempotent بنسخة (`base_version`)؛ حالات قبول/رفض/تعارض صريحة. التفصيل في `06-pwa-sync.md`.
