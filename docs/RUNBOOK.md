# Runbook — تشغيل النظام وصيانته

> للمالك أو من يديره تقنياً. كل أمر هنا جُرِّب على بيئة حقيقية إلا ما وُسم **(لم يُجرَّب هنا)**.

## 0) نظرة سريعة
```
المتصفح/PWA ──HTTPS──► Caddy ──► app (Next.js, مستخدم غير جذر, ملفات للقراءة فقط) ──► PostgreSQL 16 (شبكة داخلية فقط)
                                      └── volume: uploads (المرفقات)
خارج الخادم: نسخ احتياطية مشفّرة (age) ◄── ops/backup.sh (cron)
```
| الأمر | الغرض |
|---|---|
| `docker compose ps` / `logs -f app` | الحالة / السجلات |
| `curl -fsS https://DOMAIN/api/health` | صحة التطبيق وقاعدة البيانات |
| **الأمان ← سلامة البيانات والنسخ** (للمالك) | ميزان المراجعة، مطابقة المخزون، النسخ، آخر اختبار استعادة |

## 1) القوائم الدورية
**يومياً (دقيقة):** افتح «سلامة البيانات» — كل البنود ✔ وآخر نسخة < 26 ساعة. راجع التنبيهات في لوحة التحكم.
**أسبوعياً:** تأكد أن نسخة أسبوعية وصلت للتخزين الخارجي؛ راجع سجل التدقيق للعمليات الحساسة (رأس المال، التسويات، إعادة فتح فترة).
**شهرياً:** (1) أقفل الشهر المنتهي (القسم 8). (2) نفّذ **اختبار الاستعادة** (القسم 4) — مطلوب. (3) حدّث النظام (القسم 5). (4) `docker system prune -f` و`df -h` (القرص < 80%).
**سنوياً:** دوّر الأسرار (القسم 6) وجدّد دومين/شهادات إن لزم وراجع صلاحيات المحاسب.

## 2) النسخ الاحتياطي (مشفّر وخارجي)
**المبدأ:** يُشفَّر النسخ بمفتاح **عام** (age) على الخادم؛ **المفتاح الخاص لا يوجد على الخادم أبداً** — بحوزتك وحدك (جهازك + نسخة ورقية/خزنة). فقدان المفتاح الخاص = فقدان كل النسخ.

### إعداد أولي (مرة واحدة)
```bash
# على جهازك أنت (وليس الخادم):
age-keygen -o erp-backup-identity.txt        # احفظه خارج الخادم! السطر "public key: age1..." هو ما يُوضع على الخادم
# على الخادم:
sudo mkdir -p /opt/erp && cd /opt/erp && git clone <repo> . && cp .env.example .env
# اختر وجهاً خارجياً (S3-compatible: Backblaze B2 / Cloudflare R2 / Wasabi / …) من مزود مختلف عن مزود الـ VPS ثم:
rclone config                                 # أنشئ remote اسمه مثلاً erp-backups
```
ملف `/etc/erp-backup.env` (صلاحيات 600):
```
PGHOST=127.0.0.1  PGPORT=5432  PGUSER=<POSTGRES_USER>  PGPASSWORD=<POSTGRES_PASSWORD>  PGDATABASE=<POSTGRES_DB>
UPLOAD_DIR=/var/lib/docker/volumes/<project>_uploads/_data
AGE_RECIPIENT=age1...                         # المفتاح العام فقط
BACKUP_REMOTE=erp-backups:erp-prod            # أو مسار محلي للتجربة
ALERT_WEBHOOK=https://...                     # اختياري: يُستدعى عند الفشل
```
> قاعدة البيانات لا تفتح منفذاً للخارج: شغّل السكربت داخل شبكة Docker (`docker compose exec`) أو عرّض 5432 لـ 127.0.0.1 فقط.

### الجدولة (cron) — **(لم يُجرَّب هنا: cron/rclone)**؛ السكربتات نفسها جُرِّبت
```
17 2 * * *   . /etc/erp-backup.env && /opt/erp/ops/backup.sh daily  >> /var/log/erp-backup.log 2>&1
```
- كل يوم نسخة يومية (تُحفظ 14)؛ **كل جمعة** تُحفظ أيضاً أسبوعية (8)؛ **أول كل شهر** شهرية (12).
- يُسجَّل كل تشغيل في جدول `backup_jobs` ويظهر في شاشة «سلامة البيانات». عند الفشل: `FAILED` + إشعار webhook + رمز خروج ≠ 0.
- يتحقق السكربت من مجموع التحقق (sha256) للنسخة على الوجهة بعد الرفع.

## 3) ما جُرِّب فعلياً (محلياً، بقاعدة بيانات حقيقية)
| الاختبار | النتيجة |
|---|---|
| نسخة كاملة (قاعدة + مرفقات + manifest) مشفّرة | ✔ `BACKUP OK` + سجل `backup_jobs` |
| استعادة على قاعدة **منفصلة** + فحوص `ops/verify.sql` (ميزان، FIFO=الدفتر، لا سالب، المعادلة المحاسبية، المرقّمات، الترحيلات) | ✔ كلها PASS |
| رفض الاستعادة فوق القاعدة الحية | ✔ |
| ملف معبَّث (بايت واحد) مع/بدون ملف المجموع | ✔ يُرفض (checksum / مصادقة age) |
| مفتاح خاطئ | ✔ يُرفض |
| الاحتفاظ: 20 نسخة يومية ⇒ تبقى 14 | ✔ |
| فشل النسخ (مفتاح عام خاطئ) | ✔ `FAILED` + خروج 1 |
| اختبار استعادة شهري آلي `restore-test.sh` | ✔ `RESTORE_TEST|OK` وحُذفت القاعدة المؤقتة |

## 4) اختبار الاستعادة الشهري والتعافي من الكوارث
### اختبار شهري (لا يلمس الإنتاج)
```bash
. /etc/erp-backup.env
AGE_IDENTITY=/path/to/erp-backup-identity.txt  /opt/erp/ops/restore-test.sh      # يضع المفتاح الخاص مؤقتاً ثم يُزال
```
النتيجة المتوقعة: `RESTORE DRILL OK`. ويُسجَّل في «سلامة البيانات» (تنبيه إن تجاوز 35 يوماً).

### تعافٍ كامل على خادم جديد (الخادم الأصلي مفقود)
1. جهّز VPS جديداً كما في `docs/DEPLOYMENT.md` (حتى خطوة `docker compose up` **دون** bootstrap).
2. نزّل آخر نسخة من الوجهة الخارجية: `rclone copy erp-backups:erp-prod/<الملف>.tar.age .` (+ `.sha256`).
3. `ops/restore.sh <الملف> erp-backup-identity.txt <اسم_قاعدة_جديدة> /path/to/uploads` — يطبع فحوص `verify.sql`؛ **لا تكمل إلا والنتيجة `RESTORE OK`**.
4. وجّه `.env` (`POSTGRES_DB`) إلى القاعدة المستعادة (أو أعد تسميتها)، وانسخ المرفقات إلى volume `uploads`.
5. شغّل `docker compose up -d` (خدمة `migrate` تطبّق أي ترحيلات ناقصة تلقائياً)، ثم تحقق من «سلامة البيانات».
6. غيّر DNS إلى الخادم الجديد، **وابدأ دورة الأسرار (القسم 6)** لأن الخادم القديم يُعتبر مخترَقاً حتى يثبت العكس.
**أهداف التعافي:** RPO ≤ 24 ساعة (نسخة يومية؛ أقل يتطلب WAL archiving — غير مفعّل)، RTO ≈ ساعتان **(تقدير لم يُقَس)**.

## 5) التحديث والتراجع
```bash
cd /opt/erp && . /etc/erp-backup.env && ops/backup.sh daily          # 1) نسخة قبل أي تحديث
git fetch && git checkout <الإصدار>                                    # 2)
docker compose up -d --build                                           # 3) يبني، يطبّق الترحيلات (migrate)، يعيد تشغيل التطبيق
curl -fsS https://DOMAIN/api/health && (افتح «سلامة البيانات»)         # 4) تحقق
```
**التراجع:** الترحيلات للأمام فقط (checksum يمنع تعديل ترحيل مطبّق).
- ترحيل لم يُغيّر بنية الجداول بشكل غير متوافق: `git checkout <الإصدار السابق> && docker compose up -d --build`.
- ترحيل غير متوافق/تلف بيانات: أوقف التطبيق، استعد نسخة ما قبل التحديث إلى قاعدة جديدة (القسم 4) وبدّل `POSTGRES_DB`، ثم ارجع للإصدار السابق. **لن تُفقد إلا العمليات بعد النسخة** — لذلك التحديث في وقت هادئ.
- قاعدة: لا تحدّث في آخر الشهر قبل إقفال الفترة.

## 6) الأسرار والاسترداد
| السر | أين | التدوير/الاسترداد |
|---|---|---|
| `POSTGRES_PASSWORD`, `APP_DB_PASSWORD` | `.env` | غيّرهما في `.env` ثم `ALTER ROLE ... PASSWORD` ثم `docker compose up -d` |
| `APP_SECRET` | `.env` | **تغييره يُبطل أسرار 2FA المخزنة** ⇒ شغّل `reset-access` مع `RESET_2FA=1` وأعد تسجيل 2FA |
| مفتاح age الخاص | بحوزتك | أنشئ زوجاً جديداً، ضع العام على الخادم، **احتفظ بالقديم** لاستعادة النسخ القديمة |
| كلمة مرور المالك المنسية / 2FA مفقودة | — | على الخادم: `OWNER_USERNAME=owner NEW_PASSWORD='...' RESET_2FA=1 DATABASE_URL=... npm run reset-access` (يُلغي الجلسات ويُدقَّق) |
| اشتباه اختراق | — | (1) `docker compose stop app` (2) افحص `audit_logs` (3) دوّر كل الأسرار (4) ألغِ الجلسات: `update sessions set revoked_at=now()` (5) استعد من نسخة نظيفة عند اللزوم |

## 7) المراقبة والتنبيه
- **أداة مراقبة خارجية** (UptimeRobot أو مثيلتها) على `https://DOMAIN/api/health` كل دقيقة (يُعيد 503 إن سقطت القاعدة).
- «سلامة البيانات» تعرض ما يجب أن يبقى أخضر. أي ⛔ في الميزان/المخزون/الصندوق = **أوقف الترحيل** وراجع (القسم 9).
- السجلات JSON بلا أسرار ولا قيم SQL: `docker compose logs app | grep '"level":"error"'`.
- القرص: `df -h`؛ المرفقات تنمو مع الصور (حد 5MB للملف).

## 8) إقفال الشهر (قائمة)
1. رحّل أو احذف **كل المسودات** المؤرخة في الشهر. 2. رحّل استحقاقات الرواتب. 3. طابق الصندوق فعلياً. 4. جرد المخزون إن لزم (يعتمده المالك). 5. تأكد من «سلامة البيانات» ✔. 6. **المحاسبة ← إقفال الفترات** (المالك). 7. نفّذ تسوية الأرباح للفترة إن أردت التوزيع.
إعادة فتح شهر: المالك فقط + رمز 2FA + سبب مكتوب، ويُدقَّق.

## 9) سيناريوهات الأعطال
| العَرَض | الإجراء |
|---|---|
| الموقع لا يفتح | `docker compose ps`؛ `logs caddy app`؛ تحقق DNS/الشهادة؛ `curl http://127.0.0.1:3000/api/health` من الخادم |
| `/api/health` = 503 | القاعدة متوقفة: `docker compose logs db`؛ القرص ممتلئ؟ `docker compose restart db` |
| القرص ممتلئ | `docker system prune -f`؛ احذف سجلات قديمة؛ **لا تحذف volume القاعدة**؛ رقِّ القرص |
| التطبيق يُعيد التشغيل باستمرار | `logs app`؛ غالباً `.env` ناقص (`APP_SECRET`/`DATABASE_URL`) أو ترحيل فاشل في `migrate` |
| ⛔ ميزان/مخزون/صندوق في «سلامة البيانات» | أوقف المحاسب عن الترحيل؛ افحص آخر العمليات في التدقيق؛ شغّل `psql -f ops/verify.sql`؛ إن ثبت تلف: استعد (القسم 4) |
| ترحيل خاطئ | **لا حذف**: افتح المستند ← «عكس» بسبب (قيد معاكس). في فترة مقفلة: إعادة فتح (المالك+2FA) ثم العكس |
| تعارض مزامنة | يظهر في «المزامنة» بسببه (مخزون/صندوق/نسخة)؛ عدّل أو أعد المحاولة أو احذف محلياً |
| نسيان الرقم السري للقفل المحلي | «مسح بيانات الجهاز» (المسودات غير المزامنة تضيع — لذلك تصدير المسودات دورياً) |

## 10) الصيانة الدورية الفنية
- `docker compose exec db psql -U $POSTGRES_USER -d $POSTGRES_DB -c "VACUUM (ANALYZE)"` شهرياً (autovacuum يكفي عادةً).
- ترقية Postgres الرئيسية: نسخة + restore على إصدار جديد في قاعدة منفصلة، ثم تبديل؛ **لا ترقية في المكان**.
- تحديثات نظام التشغيل: `unattended-upgrades` مفعّل؛ أعد التشغيل في نافذة صيانة.
