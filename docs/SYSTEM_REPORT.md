# التقرير الشامل للنظام — نظام المحاسبة والمخزون والشراكة (عربي RTL)

> هذا الملف للقراءة والتحليل والتعديل. كل ما فيه مأخوذ من الكود الفعلي في الفرع `claude/accounting-partnership-phase-0-31rwoc` (مستودع `azecso/az0097`). حيث لم أتحقق من شيء ذكرتُ ذلك صراحةً.
> مسارات الملفات نسبية إلى `app/` ما لم يُذكر غير ذلك.

## 1) ما هو النظام؟

نظام ويب (PWA) بواجهة عربية من اليمين لليسار لإدارة:
- المبيعات (عروض أسعار، فواتير، تسليم، مرتجعات، سندات قبض)
- المشتريات (فواتير شراء مع تكاليف إضافية، مدفوعات الموردين، مرتجعات)
- المخزون بطريقة FIFO (مواقع، تحويلات، جرد)
- الصناديق والتحويلات بين الصناديق
- المصاريف والرواتب والسلف
- رأس المال والسحوبات ورد رأس المال
- تسوية الأرباح بين شريكين (50/50) مرتبطة بالتحصيل الفعلي
- عملتان: الدينار العراقي (أساس) والدولار
- طباعة A4 رسمية وPDF وExcel، ونسخ احتياطي واستعادة، وعمل دون إنترنت للمسودات

**قيود ثابتة في التصميم:**
- لا أرقام عائمة (floats) للمال أبداً: `decimal.js` في الكود و`NUMERIC` في قاعدة البيانات، والقيم تنتقل نصوصاً.
- دفتر القيود **للإضافة فقط** (append-only): التصحيح يتم بقيد عكسي، لا بتعديل أو حذف.
- الترقيم متسلسل بلا فجوات لكل نوع مستند وسنة.
- مستخدم مالك واحد (Owner) لكل شركة، وكل صلاحية أخرى تُمنح صراحةً.

### 4.2) حمايات على مستوى قاعدة البيانات
- **RLS** على كل جدول بحسب `company_id`، ومستخدم التطبيق ليس مالك الجداول ولا `BYPASSRLS`.
- **منع التعديل:** `forbid_mutation` على القيود وحركات النقد والمخزون وغيرها. تعديل/حذف سطر في دفتر القيود مرفوض من القاعدة نفسها.

- **دورة حياة المستند:** `guard_document_lifecycle` و`guard_line_parent` — لا يُعدَّل المستند بعد الترحيل. (المتغيّر `app.amend` يسمح بإعادة فتح مستند داخلياً أثناء «تعديل مع نفس الرقم» فقط.)
- **صلاحيات SQL:** يحصل مستخدم التطبيق على `SELECT, INSERT, UPDATE` على كل الجداول، و`DELETE` فقط على قائمة `deletable` في `scripts/migrate.ts` (جداول المسودات). أي جدول جديد يحتاج حذفاً يجب إضافته إلى هذه القائمة.
- **الترقيم:** `next_document_number(company, doc_type, year)` يضمن تسلسلاً بلا فجوات.

## 6) القيود المحاسبية لكل مستند

> الأرقام بالدينار (العملة الأساس). كل سطر يحفظ العملة الأصلية والمبلغ الأصلي وسعر الصرف المثبَّت على المستند.

### 6.1) فاتورة البيع (`sales.ts: postInvoice`)
- من 1200 (ذمم العملاء) بقيمة الصافي.
- من 4150 بالخصم (إن وُجد).
- إلى 4100 بإجمالي المبيعات.
- إذا نوع الفاتورة **نقدي**: يُنشأ سند قبض تلقائي بقيمة الفاتورة.
- إذا كان `deliveryMode = WITH_INVOICE` يُنشأ ويُرحَّل سند تسليم تلقائي → يخرج المخزون FIFO: من 5100 إلى 1300 بتكلفة الدفعات المستهلكة.
- يُتحقق من الحد الائتماني للعميل (قيمة الرصيد الحالي + الفاتورة).
- الخصم على مستوى الفاتورة يُوزَّع على السطور (الباقي على آخر سطر) لتقدير المرتجعات بدقة.

### 6.2) سند القبض (`receipts.ts: postReceipt`)
- **قبض نقدي:** من الصندوق (أو عهدة الشريك 1150) بسعر **يوم القبض**؛ إلى 1200 بسعر **الفاتورة الأصلي**؛ الباقي بلا فاتورة → 2400 رصيد دائن للعميل؛ **الفرق في الدينار → 7100** (ربح أو خسارة صرف محقق).
- **تسوية رصيد دائن:** من 2400 إلى 1200.
- **ربح موزَّع خارج النظام (للمالك فقط، قبض نقدي بالدينار فقط):** يُسجَّل في السند بلا نقد: إلى 1200 ومن 3500 مناصفة بين المالك والشريك.
- يمكن **تعديل** سند مرحّل مع بقاء رقمه (`amendReceipt`) ويمكن حذفه (عكس). سند البيع النقدي التلقائي يُعدَّل عبر فاتورته.
- القبض **صريح فقط**: لا يتم ربط تحصيل بفاتورة ضمنياً؛ يختار المستخدم الفواتير التي يقبض عليها.

### 6.3) فاتورة الشراء (`purchases.ts`)
- من 1300 (مخزون) بقيمة البضاعة **مضافاً لها التكاليف الإضافية المرسملة** (landed cost) موزّعة على الدفعات.
- تكاليف غير مرسملة → من حساب مصروف.
- إلى الصندوق (شراء نقدي) أو 2100 (آجل).
- كل سطر استلام ينشئ **دفعة مخزون (lot)** بتكلفة بالدينار وتكلفة وحدة بالعملة الأصلية.

### 6.4) دفعة المورد (`payments.ts`)
- من 2100 بسعر الفاتورة الأصلي للجزء المخصَّص (والجزء غير المخصَّص يصبح سلفة للمورد بسعر اليوم)؛ إلى الصندوق بسعر الدفعة؛ **الفرق → 7100**.

### 6.5) المرتجعات
- مرتجع مبيعات: قيد عكسي للإيراد، وإرجاع المخزون بتكلفته الأصلية، ويمكن أن يُخصم من الذمة أو يُرد نقداً أو يتحول إلى رصيد دائن.
- مرتجع مشتريات: يخفض الذمة أو يُرد نقداً، ويُخرج المخزون.

### 6.6) رأس المال والسحوبات
- **إيداع رأس مال:** من الصندوق إلى 3100 (طلب ثم اعتماد من المالك برمز 2FA دائماً).
- **سحب/رد رأس المال:** مسار منفصل (`capital-returns.ts`، البادئة CR).
- **سحوبات المالك (3200):** مبالغ يأخذها الشريك للاستعمال الشخصي؛ لا تؤثر على الربح.
- **سلف الشريك (1250)** و**ذمة الشريك (2300)** لحسابات الشريك الشخصية.

### 6.7) المصاريف والرواتب
- المصروف إما نقدي أو **مستحق** (2210) ثم يُسدَّد جزئياً أو كلياً.
- الراتب: يُولَّد استحقاق شهري (2200 ↔ 6200) ثم يُدفع.

### 6.8) الأرصدة الافتتاحية (`opening.ts`)
- لبدء الدفاتر بوضع سابق (صندوق، مخزون، ذمم عملاء، ذمم موردين) بتاريخ البداية. تُوازَن مقابل 3900 المؤقت. فواتير الذمم الافتتاحية لا تحمل ربحاً.

### 6.9) الجرد والتحويلات
- تحويل بين الصناديق (TR) — لا يغيّر الربح (مثلاً تسليم عهدة الشريك).
- جرد المخزون يولّد فروقات في 5200 ودفعات تعديل.
- تحويل مخزون بين المواقع/الشريك.

## 7) المخزون بطريقة FIFO

- كل استلام ينشئ `stock_lots` (دفعة) بتاريخ استلامها وتكلفتها.
- الصرف يستهلك الأقدم أولاً (`consumeFifo` في `lib/inventory.ts`) ويسجّل `stock_lot_consumptions`، والتكلفة تُحفظ على سطر التسليم (`cost_base`).
- المرتجعات تعيد الكمية لنفس الدفعات المستهلكة (`stock_lot_returns`).
- مطابقة المخزون مع الأستاذ متاحة كتقرير ومؤشر سلامة (`/inventory/stock`، `integrity.ts`).
- الكميات بوحدة أساس مع تحويل للوحدات الأخرى (`product_uoms`)، ودقة الكسور لكل منتج (`qty_decimals`).

## 8) العملات وأسعار الصرف

- العملة الأساس **IQD**، والثانية **USD**.
- جدول `fx_rates` يحفظ سعراً يومياً: **IQD لكل 1 USD** (مثال 1480). يُسمح بالمدى 1 إلى 100,000.
- عند إنشاء أي مستند بالدولار: إما سعر يدوي على المستند أو آخر سعر مسجّل في/قبل التاريخ. السعر **يُثبَّت** على المستند.
- مبلغ الدينار = `round(المبلغ × السعر)`.
- لا يوجد تحويل عملة داخل المستند الواحد: عملة السند يجب أن تطابق عملة الفاتورة وعملة الصندوق.
- فروق الصرف المحققة تذهب إلى 7100 عند القبض والدفع، وتدخل ضمن «الخصومات» في حساب الربح القابل للتوزيع.
- **لا توجد إعادة تقييم** لأرصدة الدولار في نهاية الفترة.

(راجع القسم 12 للملاحظات والأخطاء المرصودة.)

## 9) الأرباح وتسوية الشريكين

### 9.1) الربح المرتبط بالتحصيل (`sales.ts: invoiceProfit`)
- ربح الفاتورة (بالدينار) = صافي المبيعات − تكلفة البضاعة المسلَّمة (بعد المرتجعات).
- **الربح المرتبط بالتحصيل** = الربح المعدّل × `min(1, صافي المقبوض ÷ صافي الفاتورة المعدّل)`. أي لا يصبح الربح قابلاً للتوزيع إلا بقدر ما قُبض فعلاً.
- هو مؤشر **تقييد للتوزيع**، لا ربحاً محاسبياً جديداً.

### 9.2) التسوية (`settlements.ts: computeSettlement`)
- **E:** الربح المستحَق حديثاً = مجموع (الربح المرتبط الآن − ما أُفرج عنه في تسويات سابقة).
- **X:** الخصومات المتراكمة منذ آخر تسوية = (المصاريف + فروقات الجرد 5200 + فروق الصرف 7100) التراكمي − التراكمي السابق.
- **A:** تعديل يدوي موقَّع (موثَّق). **R:** مبلغ يحتجزه المالك (موثَّق). **L:** خسارة مرحَّلة من فترة سابقة.
- `B = E − X + A`.
  - إذا `B < 0`: تُرحَّل خسارة ولا يوجد توزيع.
  - غير ذلك: `التغطية = min(L, B)` و`D = max(B − التغطية − R, 0)`.
- التوزيع **50/50**: نصيب الشريك = `floor(D/2)` والمالك الباقي (`split5050`).
- الاعتماد للمالك فقط، ويعيد الحساب من الدفاتر الحيّة تحت قفل، ويجمّد السطور فلا تُعاد، ويسجّل التزام 2500 مقابل 3400 (أرباح موزعة).
- الدفع (`profit_payouts`) من صندوق **دينار** ضمن النقد المتاح.
- يمكن تفعيل رمز 2FA لاعتماد/دفع التسويات عبر إعداد الشركة (`profitStepUp`)، أما رأس المال وإعادة فتح الفترات فيتطلبان 2FA دائماً.

### 9.3) الربح الخارجي
- لما يكون الربح قد وُزِّع خارج النظام: يُسجَّل بمعرفة المالك عند سند القبض (قسم 6.2)، ويظهر في تقرير «الأرباح الخارجية الموزعة».

## 10) الأمان والصلاحيات

- **الدخول:** كلمة سر argon2 بحد أدنى قوة، حد محاولات، جلسات في قاعدة البيانات، كوكي HttpOnly.
- **CSRF** على كل عملية مغيّرة (رمز في الترويسة + فحص origin).
- **CSP** وترويسات أمان في الخادم.
- **الصلاحيات:** كل مورد له أفعال `view/create/edit_draft/approve/cancel/print/export`. الموارد: company, users, contacts, products, fx_rate, purchase, sales, voucher, stock_transfer, inventory_count, expense, payroll, capital, capital_withdrawal, personal, opening_balance, profit_settlement, profit_payout, period_close, journal, audit, backup, report.
- **للمالك فقط:** users، backup، إعدادات الشركة (إنشاء/تعديل)، واعتماد/إلغاء رأس المال والسحب والأرصدة الافتتاحية والتسويات والدفعات وإقفال الفترات والجرد.
- **2FA (TOTP):** إلزامي للمالك في العمليات الحرجة ما لم يُضبط `REQUIRE_OWNER_2FA=false`.
- **المرفقات:** نوع الملف يُحدَّد من محتواه (PNG/JPEG/WEBP/PDF) بحد 5MB، وتُحفظ على القرص (`UPLOAD_DIR`) وجدول `attachments`.
- **سجل التدقيق:** `audit_logs` للإضافة فقط.

## 11) الميزات التشغيلية

### 11.1) الطباعة والتصدير
- ورقة A4 رسمية موحدة (`components/official-sheet.tsx` + `.css`) لكل المستندات، مع شعار وتوقيع وتفقيط.
- PDF من الخادم عبر Chromium (`lib/pdf.ts`)، وإذا لم يتوفر يُفتح حوار الطباعة في المتصفح.
- تصدير Excel للتقارير (`exports.ts`).

### 11.2) العمل دون إنترنت (PWA)
- خزنة IndexedDB مشفّرة للمسودات، وطابور عمليات تُزامَن عند عودة الاتصال (`sync_operations`، `sync_conflicts`)، وصفحة «المزامنة» لحل التعارضات.
- `public/sw.js` و`manifest.webmanifest`.

### 11.3) الفترات المحاسبية
- إقفال شهري (`accounting_periods`): الترحيل في فترة مقفلة مرفوض، وإعادة الفتح بـ2FA.

### 11.4) التعديل والحذف
- **تعديل فاتورة مبيعات مرحّلة** مع بقاء رقمها (`amendInvoice`): تُعكس النسخة القديمة داخلياً وتُخفى، وتنشأ نسخة جديدة بنفس الرقم، والسندات المقبوضة عليها تتبعها. مرفوض إذا وُجدت مرتجعات أو كانت داخل تسوية معتمدة أو لها تسليمات منفصلة مرحّلة.
- **حذف** فاتورة أو سند: عكس داخلي (القيد الأصلي يبقى في الدفتر) مع إخفائه من القوائم.
- التعديل بنفس الرقم **غير مُنفَّذ** حالياً لفواتير الشراء ودفعات الموردين والمصاريف (المتاح هو الحذف/العكس).

### 11.5) النسخ الاحتياطي والسلامة
- `ops/backup.sh`، `restore.sh`، `restore-test.sh`، `verify.sql`، وصفحة المالك «سلامة البيانات والنسخ» (`/settings/backup`) مع فحوص: ميزان المراجعة، توازن القيود، مطابقة المخزون، ومراجعة سجل النسخ (`backup_jobs`).

### 11.6) تصفير البيانات (للمالك)
- صفحة `/settings/reset`: تنزيل نسخة JSON كاملة ← كتابة عبارة التأكيد ← رمز 2FA ← تنفيذ.
- يحذف كل ما أُدخل (مستندات، حركات، عملاء، موردون، منتجات، موظفون، مرفقات عدا الشعار والتوقيع) ويعيد الترقيم من 1، ويُبقي المستخدمين والصلاحيات والحسابات والصناديق والشركاء والإعدادات.
- مُنفَّذ بدالة `reset_company_data` (migration 0013، SECURITY DEFINER)، تعمل فقط في قاعدة بشركة واحدة.

## 12) الملاحظات والأخطاء المرصودة (من مراجعة الدولار)

أُجريت مراجعة بتشغيل مثال رقمي: شراء 100 قطعة بـ7$ بسعر 1480، بيع 10 قطع بـ10$ بسعر 1500 (فاتورة 100$ = 150,000 د.ع)، قبض 100$ بسعر 1520.

**ما يعمل بشكل صحيح:** سعر الصرف يُثبَّت على المستند، قيد البيع 150,000، التكلفة 103,600 (10×7×1480)، القبض يدخل صندوق الدولار، الدفتر متوازن.

**المشاكل:**
1. **فرق الصرف يتولّد على كل قبض:** قُبض 152,000 د.ع نقداً مقابل ذمة 150,000، فدخل 2,000 د.ع كربح صرف في 7100، بينما الصفقة بالدولار ربحها 30$.
2. **الأرباح والتسويات بالدينار فقط:** دفع حصة الشريك يرفض أي صندوق غير دينار (`settlements.ts` يتحقق من `IQD`).
3. **لا صندوق عهدة بالدولار للشريك** (عهدة الشريك 1150 دينار فقط).
4. **الربح الخارجي** يقبل سنداً نقدياً بالدينار فقط.
5. **سعر الصرف بلا حماية من الخطأ:** يقبل أي قيمة بين 1 و100,000 (إدخال 148 بدل 1480 يمر). وإذا تُرك الحقل فارغاً يُؤخذ آخر سعر قبل التاريخ حتى لو قديماً، بلا تنبيه.
6. واجهة السعر لكل 1$، وليس لكل 100$ كما اعتاد المستخدم، ولا يظهر معادل الدينار أثناء إدخال الفاتورة.
7. **لا إعادة تقييم** لأرصدة الدولار في نهاية الفترة (صندوق، ذمم عملاء، ذمم موردين).
8. زر تسوية الرصيد الدائن للعميل يظهر لفواتير الدينار فقط.

**لم تُراجَع بعد:** مرتجعات الدولار، مصاريف الدولار، كشف حساب العميل بالدولار، التقارير على فواتير بسعرين مختلفين، وشكل طباعة فاتورة الدولار بالتفصيل.

## 13) قيود وحدود معروفة

- الشركاء: شريكان فقط وبنسبة 50/50 ثابتة. أكثر من شريكين أو نسب مختلفة غير مدعوم.
- التعديل بنفس الرقم لمستندات الشراء والمصاريف ودفعات الموردين غير مُنفَّذ.
- Docker وCI لم يُشغَّلا فعلياً، ولم يُجرَ اختبار اختراق، وتخزين النسخ السحابي والجدولة (cron) لم يُختبرا.
- توليد PDF بالـChromium المضمَّن لم يُتحقق منه على الاستضافة الفعلية للمستخدم، وقد تحدّه ذاكرة الباقة المجانية.
- اختبار `performance.test.ts` متقطع (يفشل أحياناً عند ضغط التوازي) ولم يُعرف سببه الجذري.
- أمر `lint` في المشروع هو `lint-money.mjs` + `tsc`، وليس ESLint.

## 14) دليل التعديل: أين أغيّر ماذا؟

| الهدف | الملفات |
|---|---|
| منطق فاتورة البيع/القيد/الربح | `src/lib/services/sales.ts` |
| سند القبض وفروق الصرف | `src/lib/services/receipts.ts` |
| دفع الموردين | `src/lib/services/payments.ts` |
| الشراء وتكلفة المخزون | `src/lib/services/purchases.ts`, `src/lib/inventory.ts` |
| سعر الصرف وقواعده | `src/lib/services/fx.ts`, `common.ts: resolveRate`, `src/lib/money.ts`, واجهة `settings/fx/page.tsx` ونموذج `sales/new/page.tsx` |
| تسوية الأرباح | `src/lib/services/settlements.ts`, `profits.ts` |
| دليل الحسابات / الترقيم | `scripts/bootstrap.ts` (+ migration لأي حساب جديد لشركات قائمة) |
| صلاحيات جديدة | migration يُدرج في `permissions`، و`authz.ts` للقالب الافتراضي |
| قائمة الشاشات | `src/app/(app)/layout.tsx` (المصفوفة `NAV`) |
| تقارير جديدة | `analytics.ts` / `reports.ts` + صفحة في `src/app/(app)/reports` |
| تخطيط الطباعة | `components/official-sheet.tsx` و`.css` و`print-docs.ts` |
| جدول جديد | ملف migration جديد برقم تالٍ + سياسة RLS + (إن لزم حذف) إضافته إلى `deletable` في `scripts/migrate.ts` |

**قواعد يجب احترامها عند أي تعديل:**
1. لا تستخدم أرقام JS عائمة للمال؛ استعمل `d()` من `money.ts`. (`npm run lint` يفحص ذلك.)
2. أي ترحيل يمرّ عبر `postJournal` ويجب أن يتوازن.
3. لا تعدّل migration مُطبَّقاً (يُفحص بالـchecksum)؛ أنشئ ملفاً جديداً.
4. أضف اختباراً في `tests/` (استعمل `tests/world.ts`)، وشغّل `npm test`، وللواجهة سيناريو في `e2e/`.
5. اجعل نقاط الـAPI عبر `secured({...})` مع الصلاحية الصحيحة.

## 15) التشغيل

```bash
cd app
npm install
# قاعدة PostgreSQL 16 جاهزة، ثم:
DATABASE_URL=postgres://owner@host/db APP_DB_USER=erp_app APP_DB_PASSWORD=... npm run migrate
DATABASE_URL=... COMPANY_NAME="شركتي" OWNER_USERNAME=owner OWNER_PASSWORD='...' npm run bootstrap
npm run build && npm start          # أو docker-compose up
npm test                            # اختبارات الوحدة/التكامل (تحتاج PostgreSQL)
E2E_ADMIN_URL=postgres://postgres@127.0.0.1:5432 ./e2e/run.sh   # سيناريوهات المتصفح
```

متغيرات مهمة: `DATABASE_URL` (مستخدم التطبيق المحدود)، `UPLOAD_DIR`، `COOKIE_SECURE`، `REQUIRE_OWNER_2FA`، `CHROMIUM_PATH`، `API_RATE_LIMIT`. التفاصيل في `docs/DEPLOYMENT.md` و`docs/RUNBOOK.md`.
